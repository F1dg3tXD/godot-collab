# Godot Collab relay server

A small, optional dedicated server that lets two Godot editors collaborate over
the internet **without port forwarding**. The session host and every client make
outbound ENet/UDP connections to the relay; the relay forwards opaque packets
between them.

The same deployment can also run the **rendezvous service** (a tiny HTTP/Python
helper) so hosts can offer short, human-shareable invite codes. The Docker image
runs both together; see [Docker](#docker-recommended-for-server-hardware).

It is deliberately *not* an application server:

- It never parses scene, workspace, file or transfer payloads — it only moves the
  already-framed bytes (`CollabRelayProtocol`).
- It holds rooms in memory only and writes nothing to disk.
- It is not an authentication authority: it forwards the session-token
  handshake between peers, and enforces the room token it was given at
  registration time.
- Traffic is plain ENet/UDP; it is **not encrypted**. Do not use it for
  confidential data without an external tunnel (for example WireGuard/SSH).

## Running

The relay reuses the add-on's Godot classes, so run it with a Godot 4.7.2 binary
from a project that has the add-on installed (this repository works).

> **First-run note.** `class_name` types (`CollabRelayServer`, `CollabLog`, …) are
> resolved from `.godot/global_script_class_cache.cfg`, which is generated by the
> editor and is **not committed**. On a fresh checkout, running the script
> directly fails with `Could not find type "CollabRelayServer"`. Import the
> project once to build the cache:

The wrapper script does that automatically and then starts the relay:

```sh
GODOT=/path/to/godot tools/relay_server/run.sh --port 45900
```

Equivalently, without the wrapper:

```sh
godot --headless --import            # once, to build the class cache
godot --headless --script tools/relay_server/relay_server.gd -- --port 45900
```

Options (after `--`):

| Option | Default | Meaning |
| --- | --- | --- |
| `--port <n>` | `45900` | UDP port to listen on |
| `--max-clients <n>` | `64` | Maximum simultaneous ENet clients |
| `--bind <address>` | `*` | Bind address (`*` = all interfaces) |
| `--projects-dir <dir>` | `tools/relay_server/projects` | Live project mirror directory (pass `""` to disable) |
| `--help` | | Show usage |

Environment: `GODOT_COLLAB_RELAY_PASSWORD` (optional) protects the relay with a
shared password.

Open the chosen UDP port in the relay host's firewall. The relay does **not**
need to be reachable from the editors on any port other than this one.

### Requiring a password

Set `GODOT_COLLAB_RELAY_PASSWORD` to require every host and client to present the
same shared secret in the add-on's **relay password** field:

```sh
GODOT_COLLAB_RELAY_PASSWORD='choose-a-secret' \
  GODOT=/path/to/godot tools/relay_server/run.sh --port 45900
```

`relayctl.sh`, `run.sh`, and the Docker entry point all inherit the variable.
The relay hashes it (SHA-256) and compares in constant time; a missing or wrong
password is rejected before a room can be created or joined. The value is never
logged, written to `EditorSettings`, or embedded in `gc1`/`gc2` invitation codes,
so share it with collaborators out of band. Without the variable the relay
remains open, as before. Password support uses relay protocol version `2`; every
participant must run a matching add-on build.

### Running in the background (relay + rendezvous + mirror)

`relayctl.sh` starts **all** bundled services together — the relay, the
short-code rendezvous, and the live project mirror — writes PID files and logs
under `tools/relay_server/run/`, and stops/restarts them cleanly:

```sh
GODOT=/path/to/godot tools/relay_server/relayctl.sh start
tools/relay_server/relayctl.sh status
tools/relay_server/relayctl.sh restart --port 45900 --rendezvous-port 9080
tools/relay_server/relayctl.sh stop
```

Options (for `start`/`restart`, all also settable as environment variables):
`--port`, `--bind`, `--max-clients`, `--rendezvous-port`, `--rendezvous-bind`,
`--projects-dir`, `--godot`. The resolved configuration is remembered in
`run/config.env`, so `status` reports the ports actually in use. Logs are
`run/relay.log` and `run/rendezvous.log`; `START_TIMEOUT` (default 30 s) bounds
the readiness wait. `run/` is gitignored.

## Docker (recommended for server hardware)

The image installs a pinned, checksum-verified Godot 4.7.2 headless binary and
generates the class cache during the build, so no editor or import step is needed
at run time. It runs **both** the relay (UDP `45900`) and the rendezvous service
(TCP `9080`) in one container. Build from the repository root:

```sh
docker build -f tools/relay_server/Dockerfile -t godot-collab-relay:4.7.2 .
docker run --rm -p 45900:45900/udp -p 9080:9080/tcp godot-collab-relay:4.7.2
```

Or with Compose (from `tools/relay_server/`):

```sh
docker compose up -d --build

# Require a shared password (Compose passes the host environment through):
GODOT_COLLAB_RELAY_PASSWORD='choose-a-secret' docker compose up -d --build
```

The container publishes `45900/udp` (relay) and `9080/tcp` (rendezvous). Publish
the rendezvous port only if you want short codes and HTTPS is not fronting it —
otherwise short-code registration fails and the host falls back to the long
`gc2.…` invitation, which still works. Put the relay behind the same firewall
treatment as any UDP service, and expose it over `443`/WireGuard if you need
privacy (see the encryption note above).

### Container environment

| Variable | Default | Meaning |
| --- | --- | --- |
| `RELAY_PORT` | `45900` | Relay UDP port (ignored if CLI args are passed) |
| `RELAY_BIND` | `*` | Relay bind address |
| `RELAY_MAX_CLIENTS` | `64` | Max ENet clients on the relay |
| `RENDEZVOUS_PORT` | `9080` | Rendezvous HTTP port |
| `RENDEZVOUS_BIND` | `0.0.0.0` | Rendezvous bind address |
| `GODOT_COLLAB_RELAY_PASSWORD` | *(unset)* | Require this shared password from every host/client |

Command-line arguments (for example `--port 45900`) are forwarded to the relay.
Either service stopping shuts the container down.

## How editors use it

Relay mode is the default hosting path (uncheck **Use a relay server** only for
direct LAN hosting).

1. In the dock, make sure **Use a relay server** is ticked and enter the relay
   address (`host` or `host:port`). If the relay is password-protected, also
   enter its password in the **relay password** field on both sides.
2. Click **Host**. The dock generates a room, a session token, and a `gc2.…`
   invitation that embeds the relay endpoint, the room, the token, and the
   rendezvous URL. If the **short invite code** option is enabled and the
   rendezvous is reachable, a six-character code is registered instead.
3. Share either invitation:
   - **Long `gc2.…` code** — contains everything. A client that pastes it is
     auto-configured: relay address, port, and the rendezvous URL are written to
     settings, so future **short codes** work on that client with no manual setup.
   - **Short code** (for example `AB12CD`) — the client must already know the
     rendezvous URL (for example because it previously pasted a long code from
     the same server, or it was set in the dock).
4. The joining editor resolves the code to the relay endpoint and joins the room.

The relay assigns the host application id `1` and clients `2, 3, …`, mirroring
direct-connect ids, so the rest of the add-on is unchanged. When the host leaves,
the relay closes the room and disconnects its clients.

## Rendezvous service

The rendezvous is a small HTTP service (`tools/rendezvous_server/rendezvous_server.py`,
Python 3, standard library only) that maps a short code to connection info:
either a `direct` endpoint or a `relay` room. It stores entries in memory with a
TTL and never sees session traffic. Endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/register` | Register a code (direct or relay) with a TTL |
| `GET` | `/lookup?code=…` | Resolve a code to its connection info |
| `POST` | `/unregister` | Remove a code (requires its token) |
| `GET` | `/health` | Liveness probe |

Run it directly with `python3 tools/rendezvous_server/rendezvous_server.py
--port 9080`, or let the Docker image run it alongside the relay.

## Limits

- Rooms are per-relay-process and vanish when the host disconnects (or on
  restart). There is no persistence.
- A room accepts one host and up to `MAX_ROOM_MEMBERS` (32) participants.
- Only the host may kick a participant.
- Authentication is the room token plus, optionally, the shared relay password
  (`GODOT_COLLAB_RELAY_PASSWORD`). Without a password, anyone who learns a room
  code *and* its token can join. Treat invitations as temporary credentials, and
  use a password on any relay reachable from the public internet. Neither is
  encryption and neither identifies individual users.
